# Avito Retrieval — генерация кандидатов для поиска услуг

Решение тестового задания Авито по генерации кандидатов для поиска услуг.

Для каждого поискового запроса необходимо выбрать из корпуса до 50 наиболее релевантных объявлений, которые затем могут быть переданы на следующий этап ранжирования. Основная метрика — **Recall@50**, поэтому ключевая цель решения — обеспечить высокую полноту кандидатов: если релевантное объявление не попало в top-50, последующий ранжирующий этап уже не сможет его вернуть.

Лучший результат, полученный на внешнем benchmark:

**Recall@50 = 0.478002 (~0.48)**

Финальная очищенная версия pipeline была дополнительно проверена на воспроизводимость двумя независимыми последовательными запусками и получила **Recall@50 = 0.475997**. Полученные CSV-файлы совпали byte-for-byte.

## Идея решения

Финальный pipeline — гибридная retrieval-система из нескольких независимых источников кандидатов и небольшого supervised reranker.

Для каждого запроса строятся кандидаты из пяти источников:

1. **Character TF-IDF по заголовкам**
   - `char_wb`
   - n-gram: `3–5`
   - `min_df=2`

   Такой поиск устойчив к словоформам, частичным совпадениям и небольшим различиям в написании.

2. **BM25 по заголовкам**

   Используется для точного лексического совпадения терминов запроса и объявления.

3. **multilingual-e5-small по заголовкам**

   Семантический retrieval на open-source модели `intfloat/multilingual-e5-small`.
   Запросы кодируются с префиксом `query:`, объявления — с `passage:`.
   Embeddings нормализуются, после чего similarity считается через dot product.

4. **BM25 по параметрам объявления**

   В запрос добавляется `search_infm_params_text`, если фильтры присутствуют. Это позволяет учитывать признаки услуги, которые могут отсутствовать в заголовке.

5. **TF-IDF по описанию**

   Используются первые 512 символов `item_description_raw` как дополнительный recall-сигнал.

Каждый источник возвращает до **100 кандидатов**. После объединения и удаления дублей формируется общий пул кандидатов.

## Reranker

Финальные 50 объявлений выбираются линейным reranker.

Для каждого кандидата строятся 19 признаков:

- score каждого из 5 retrieval-источников;
- rank в каждом из 5 источников;
- флаг присутствия в каждом из 5 источников;
- количество источников, которые нашли кандидата;
- совпадение `search_location_id` и `item_location_id`;
- длина поискового запроса;
- длина заголовка объявления.

Для обучения используются позитивные объявления из `train.parquet` и до **25 негативных кандидатов на один positive**.

Модель:

- `StandardScaler`;
- `LogisticRegression`;
- `class_weight="balanced"`;
- `C=1.0`;
- `solver="lbfgs"`;
- `random_state=42`.

Линейная модель была выбрана как простой и интерпретируемый способ объединить несколько retrieval-сигналов. Более сложный tree-based reranker давал только небольшой локальный прирост, поэтому в финальной версии был оставлен более простой вариант.

## Какие данные и признаки используются

Непосредственно в retrieval и reranker используются следующие признаки запроса:

- `search_query`;
- `search_infm_params_text`;
- `search_location_id`.

Для построения уникального поискового контекста и локальной валидации дополнительно учитываются:

- `search_is_delivery_search`;
- `search_category`.

Из признаков объявления непосредственно используются:

- `item_title_raw`;
- `item_description_raw`;
- `item_infm_params_text`;
- `item_location_id`.

Основной фокус был сделан на текстовой релевантности и location-сигнале. Остальные структурированные признаки (`item_category_id`, `item_microcat_id`, цена, рейтинг, координаты и другие) в финальный pipeline не вошли.

## Локальная валидация

Обычный случайный split строк для этой задачи может давать слишком оптимистичную оценку: одинаковые или почти одинаковые запросы способны оказаться одновременно в train и validation.

Поэтому основной split строится по **нормализованному тексту запроса**:

- перевод в lower case;
- `ё → е`;
- нормализация пробелов;
- одинаковый нормализованный запрос целиком попадает только в одну часть выборки.

Разбиение:

- train — 80%;
- dev — 10%;
- holdout — 10%;
- seed — `42`.

Дополнительно используется secondary split по полным поисковым контекстам как sanity-check.

Основные результаты финальной конфигурации:

| Оценка | Recall@50 |
|---|---:|
| Primary dev | 0.361902 |
| Primary holdout | 0.359428 |
| External benchmark, reproducible final pipeline | 0.475997 |
| External benchmark, best submission | **0.478002** |

Primary validation намеренно строже случайного разбиения: одинаковые нормализованные запросы не переходят между train/dev/holdout, поэтому локальные и внешние значения метрики напрямую сравнивать не следует.

## Анализ ошибок

В ходе работы были выделены несколько типичных проблем retrieval:

- **чисто лексический поиск** теряет семантически близкие формулировки — для этого добавлен E5;
- **семантический поиск** иногда возвращает тематически похожие, но менее точные объявления — его сигнал объединяется с BM25 и TF-IDF;
- полезная информация не всегда находится в title — поэтому отдельно используются `item_infm_params_text` и description;
- разные retrieval-методы имеют разные шкалы score — их результаты не суммируются вручную, а передаются в обучаемый reranker;
- один retrieval-источник может пропустить релевантный объект — поэтому используется объединение нескольких независимых источников;
- совпадение локации используется как дополнительный сигнал в reranker;
- возможные ошибки формата submission проверяются отдельным `audit_submission()` до завершения программы.

Главное оставшееся ограничение — часть релевантных объявлений не попадает в финальный top-50. Без отдельного измерения Recall объединённого пула кандидатов нельзя полностью разделить потери между этапом retrieval и последующим reranking.

Возможные направления дальнейшего улучшения — более широкое использование category/microcategory, географических и других структурированных признаков, а также более детальный error analysis по типам запросов.

Работа выполнялась в ограниченные сроки, поэтому основной фокус был сделан на наиболее значимых для Recall@50 направлениях: корректной валидации, нескольких независимых retrieval-каналах, их объединении и воспроизводимом финальном pipeline.

## Использование ИИ

При выполнении задания ИИ-инструменты использовались как вспомогательный инструмент: для обсуждения отдельных идей, консультаций по реализации, code review, рефакторинга и проверки формулировок в документации.

Основная работа над решением — построение pipeline, выбор подходов, проведение экспериментов, локальная валидация, анализ результатов и финальная проверка — выполнялась самостоятельно. ИИ использовался скорее как дополнительный собеседник и средство проверки идей, а не как источник готового решения.

ИИ не используется в финальном pipeline как внешний inference API и не участвует в генерации `answer.csv`.

## Подготовка данных

Исходные parquet-файлы не хранятся в репозитории.

Перед запуском необходимо положить их в `data/`:

```text
data/
├── train.parquet
├── benchmark_queries.parquet
└── benchmark_items.parquet
```

Ожидаемые данные:

- `train.parquet` — обучающие пары запрос–объявление;
- `benchmark_queries.parquet` — запросы benchmark;
- `benchmark_items.parquet` — корпус объявлений benchmark.

## Локальный запуск

Требуется Python 3.12.

Создание окружения:

```bash
python3.12 -m venv venv
source venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
```

Генерация submission:

```bash
python -m src.submission --output answer.csv
```

На выходе будет создан файл `answer.csv` с колонками:

```text
query_id,answer
```

Для каждого запроса возвращается до 50 уникальных `item_id`.

### Open-source модель

Для semantic retrieval используется:

```text
intfloat/multilingual-e5-small
```

При первом запуске `sentence-transformers` загружает веса модели с Hugging Face. После загрузки весь inference выполняется локально; внешние inference API не используются.

На Apple Silicon при доступности используется MPS, в остальных случаях — CPU.

## Docker

Docker-образ использует CPU-версию PyTorch.

Сборка:

```bash
docker build -t avito-retrieval .
```

Запуск с локальными parquet-файлами:

```bash
docker run --rm   -v "$(pwd)/data:/app/data:ro"   -v "$(pwd):/output"   avito-retrieval   python -m src.submission --output /output/answer.csv
```

Данные монтируются в контейнер read-only, а итоговый `answer.csv` записывается в корень локального проекта.

## Проверка submission

После генерации `submission.py` автоматически проверяет итоговый CSV:

- ровно две колонки: `query_id`, `answer`;
- все benchmark-запросы присутствуют ровно один раз;
- не более 50 item ID в строке;
- нет повторяющихся item ID;
- каждый item ID имеет требуемый формат;
- каждый item ID существует в `benchmark_items.parquet`;
- повторное чтение CSV не изменяет данные.

Это позволяет отлавливать ошибки формата до загрузки файла на платформу.

## Воспроизводимость

Для deterministic частей pipeline используется фиксированный seed `42`, стабильная сортировка и явное разрешение ties.

Финальный pipeline был проверен двумя независимыми последовательными запусками в одном окружении: полученные CSV-файлы совпали byte-for-byte.

Численные результаты neural inference могут зависеть от вычислительного backend и аппаратной платформы, поэтому для максимально близкого воспроизведения рекомендуется использовать зафиксированные версии зависимостей и один и тот же backend.
